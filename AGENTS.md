# AGENTS.md

> **New to this repo?** Read [docs/AGENT_CODEBASE_OVERVIEW.md](docs/AGENT_CODEBASE_OVERVIEW.md) first for architecture, file map, and doc workflow. This file is runtime ops and gotchas only.

## Cursor Cloud specific instructions

**StatKeeper** is a mobile-first React web app for tracking sports statistics in real time. It uses React 18 + TypeScript + Vite + Tailwind CSS 3.

### Services

| Service | Command | Port |
|---|---|---|
| Vite dev server | `pnpm dev` | 5173 |

### Key Commands

See `package.json` scripts. Standard commands:
- `pnpm dev` — start dev server (binds `0.0.0.0:5173`)
- `pnpm build` — TypeScript check + production build
- `pnpm lint` — ESLint
- `pnpm preview` — serve production build

### Gotchas

- `pnpm.onlyBuiltDependencies` in `package.json` allowlists `esbuild`; no interactive `pnpm approve-builds` needed.
- The app uses `HashRouter` (`/#/path`), not `BrowserRouter`. URLs in the browser will look like `http://localhost:5173/#/game`.
- **Auth:** Supabase auth supports email/password plus Google OAuth. The client uses `auth.flowType: 'pkce'` so OAuth returns with a query `code` instead of token fragments that collide with HashRouter. `AuthContext.signInWithGoogle()` uses `signInWithOAuth({ provider: 'google', redirectTo })`; redirect URL is `window.location.origin + window.location.pathname` so local dev returns to `http://localhost:5173/` and GitHub Pages returns to `/cursor-default/`. Google/Supabase provider setup is external; migration `034_google_auth_profile_defaults.sql` updates new-user profile defaults for Google metadata. `/settings/account` loads/repairs `profiles`, edits `profiles.display_name`, lists `getUserIdentities()`, and starts manual Google linking with `linkIdentity`; Supabase manual identity linking must be enabled for the button to succeed. Local Google client JSON belongs in `.creds/`, which is gitignored.
- **App access (SEC-5):** Migration `039_app_level_access.sql` adds active/pending/suspended account status and a separate user/app-admin role. `enforce_app_access_request` is the PostgREST pre-request hook, so non-active sessions are blocked before Data API table and RPC calls; `get_my_app_access` remains available for the early `App.tsx` gate. The shared fetch wrapper emits an access-denied event on `APP_ACCESS_*`, allowing `AuthContext` to unmount the live app immediately; focus/online/one-minute checks are the fallback. App-admin management lives in Settings -> Advanced without bypassing team RLS. Run `supabase/scripts/bootstrap_app_admin.sql` manually with an existing profile email after applying 039. Realtime/Storage require separate enforcement if added later.
- **Access audit (SEC-6):** Migration `040_access_audit_trail.sql` adds immutable `access_audit_events`. Triggers record member invite/accept/decline/remove/role changes, invite-link create/redeem/revoke, and app-access changes without tokens; no history is backfilled. `get_access_audit_events` returns team-scoped history to accepted owner/admin users and global history to active app admins. Team Manage and Settings -> Advanced use `AuditTrailPanel`; direct client writes are denied. `player_merge_audit` stays separate, and guardian/stat/recorder/game event families remain follow-ups.
- **Team access (SEC-1/SEC-2):** Migrations `035_team_access_hardening.sql` and `036_viewer_team_role.sql` make accepted membership authoritative and add a read-only `viewer` role. Direct `team_members` writes use invite/member RPCs; owner/admin/scorer/viewer UI gates come from `src/lib/teamPermissions.ts`; scorers can track accepted-team games, while viewers get read-only team, roster, schedule, live-game detail, and final-stat views. `can_track_team_games` and RLS deny viewer game/stat/checkout/shot writes; finalized games reject normal raw writes for every role. Player identity remains creator/guardian scoped even for team admins.
- **Team invite links (SEC-3):** Migration `037_team_invite_links.sql` adds manager-created, single-use scorer/viewer links with a 7-day UI expiry. Team Manage lists active links with Copy/Revoke; `/#/invite/:token` resolves limited context before auth, preserves the route through email/password or Google OAuth, and requires confirmation before joining. Direct table access is denied; create/list/redeem/revoke use narrow RPCs.
- **Player guardianship (SEC-4):** Migration `038_guardianship_hardening.sql` replaces direct guardian writes and broad player updates with contextual claim/list/remove and identity-only update RPCs. Claims require an active player on the selected team plus accepted owner/admin/scorer access; viewers cannot claim. Creator, self, or an owner/admin of a team containing the player can remove a link. A DB trigger creates guardian links for new non-placeholder player creators. Team Manage keeps jersey/roster fields manager-only while creators and guardians can edit first/last/nickname and manage visible guardian relationships.
- **Navigation shell (NAV-1):** `/` and `/sports` are sport choice only. Sport work happens at `/sport/:sportId` (for example `/sport/basketball`) with active game, parked games, New Game, Teams, Cloud Games, and Season Stats actions. Existing game-flow routes (`/setup`, `/players`, `/checkout`, `/game`, `/summary`) remain direct routes. The compact authenticated shell links to Sports and Settings, but is hidden on `/game` to keep live tracking focused. Sport dashboard cloud links use query params: `/teams?sport=...`, `/games?sport=...`, `/leaderboard?sport=...`.
- **Settings routing (NAV-2):** `/settings` and `/settings/account` show profile/session controls, `/settings/app` owns enabled sport toggles, `/settings/sports` is the sport settings index, `/settings/sports/basketball` owns basketball-only preferences, `/settings/data` owns local parked-game import/export, cloud shortcuts, and Seasons, and `/settings/advanced` owns player merge plus destructive data-management tools. Legacy `#/admin` redirects to `#/settings`.
- **Court capture (basketball):** The half-court lives **inline on Game Tracker** (`#/game`) — tapping the court opens `CourtEventPopup` (Made/Miss stores a located shot via `ADD_SHOT`; the Log for picker can switch the active player before logging; the 2PT/3PT segmented chip defaults from court location but can be overridden before logging; Off/Def Reb, Steal, Block, Assist are stat-only `INCREMENT_STAT`). The full stat grid stays below the court as a second, additive input path. The chart **filters by the selected chip** (individual → their shots; team ★ → that side's union; leading **All** chip → everything) via `src/lib/shotChartViews.ts`; the "All" view changes display only — recording always targets `activePlayerId`. Same filtering on the Game Summary shot chart tab (defaults to All). **F9 missed-shot rebound prompt:** opt-in under Settings → Sports → Basketball (`statkeeper_settings.courtCapture.reboundPromptAfterMiss`); after Missed, Off Reb defaults to the missed-shot side's team pseudo-player and Def Reb defaults to the opposite side, with candidate chips to switch before dispatching a separate `INCREMENT_STAT`. **Cloud game review (F3):** the Summary tab loads **all recorders'** shots (`loadGameShotChartForReview`, one recorder per player: primary → creator → lowest id via `src/lib/shotChartReview.ts`) as display-only local state — never dispatched into `GameState.shotChart`; Cloud Games cards show a "🏀 chart" pill when a game has shots. Legacy `#/shot-chart` **redirects** to `#/game`. **Dev-only SVG preview:** `#/dev/shot-chart` loads sample shots without auth (`ShotChartPreview`); see `docs/REGRESSION_TESTING.md` §4d.
- **Recent-events undo (F12):** The bottom Game Tracker Undo opens `RecentEventsPopup`, labels recent `actionLog` entries with `src/lib/actionLogLabels.ts`, and still unwinds strictly through the newest `UNDO` entry. Older rows are context only; arbitrary out-of-order undo is deferred.
- **Assist-linking (F7):** After a made court shot, `CourtEventPopup` can show an optional **Assisted by?** step for same-side individual teammates from `src/lib/assistCandidates.ts`; choosing one dispatches the shot first, then a plain `INCREMENT_STAT(ast)` for the assister. No reducer/data-model change; F12 shows the two undo rows.
- **Popup stat line (F8):** `ShotChartPanel` computes `formatCompactGameStatLine(sport, effectivePlayer.stats)` and passes it to `CourtEventPopup`; the line is display-only context under **Log for** and updates with the F6 player switch.
- Game state uses local multi-game parking: `statkeeper_games_manifest` tracks `activeLocalGameId` plus parked summaries, each game is stored at `statkeeper_game:{localGameId}` with per-record dirty/revision sync metadata, and `statkeeper_game` remains a legacy/active mirror. P0 parks/resumes multiple local games across sports; P1 drains dirty parked games through the local sync queue; P2 hardens cloud sync by resolving roster/player rows before new `games` inserts and best-effort rolling back a just-created game if child writes fail; P3a caps local parked games at 12 and adds Settings export/import plus quota/max-count errors; P3b makes Settings import a parked-only merge that keeps existing local ids, skips invalid/at-cap rows with reason counts, and rolls back failed import batches. **Integrity guards** in `src/lib/gameSyncFingerprint.ts`: block discard/wipe of cloud-bound unsynced games (`shouldBlockDiscardUnsyncedGame`); skip sign-in auto-hydrate when the active local session is bound to a different cloud `gameId`; reject skipped-final sync success when the sync-start snapshot **or** post-await latest state still has unsynced edits. Historical orphan cleanup/full transactional sync/IndexedDB storage remain future work — see `docs/PLAN_MULTI_GAME_PARKING.md`. To reset state, use the "New Game" flow or clear localStorage.
- Sport configurations live in `src/config/sports.ts`. A `SportConfig` entry makes a sport discoverable in generic UI; full support may also require sport-specific tracker, rules, settings, and summary surfaces. See `docs/PLAN_SOC_0_SOCCER_PRODUCT_MODEL.md` for the soccer pattern. Soccer's shared event foundation is also intended for a later basketball migration; see `docs/PLAN_BASKETBALL_EVENT_MODEL_ROADMAP.md`.
- **Shared event foundation (SOC-1/SOC-2A/BKE-1A):** `GameState.eventStream` is `null` for legacy aggregate-only games and versioned when events are authoritative. Generic validation/migration/quarantine, deterministic ordering/projection, revisioned mutations, and isolated cloud transport live in `src/lib/gameEvents/`; `applyGameEventMutations` applies distinct update/delete/restore targets atomically and validates only the final candidate projection. `GameEventTeamSide` includes `neutral`, but definitions must opt in and migration 042 still rejects neutral cloud rows until BKE-4A. `src/lib/sportGameState/` owns the sport-state union/dispatch/fingerprint and fail-closed legacy aggregate capability: Basketball, Baseball, Football, and Hockey may use aggregate sync; Soccer and unknown ids may not fall through when state normalization returns null. Production Soccer definitions/projectors remain in `src/lib/soccer/` and stay narrowed to tracked/opponent. Do not initialize streams for existing basketball games or treat aggregate snapshot sync as successful raw-event sync.
- **Basketball event foundation (BKE-1/BKE-2):** `src/lib/basketball/` owns version-1 immutable rules/setup, stable tracked/opponent participants, lifecycle/stat/administrative event definitions, deterministic projection, and checked setup/capture/correction commands. Shooting, free throws, playmaking, defense, turnovers, score adjustments, fouls, ejections, charged/neutral timeouts, manual minutes, period team fouls, bonus, disqualification, and team technicals are event-derived. `courtGeometry.ts` is shared by legacy and event paths. A development-only, local-only setup toggle stamps top-level `gameDataAuthority: 'sport_events'` before game info; Player Setup snapshots non-pseudo participants and atomically initializes the stream plus Period 1. Healthy marked games route court, direct grid, score, foul, free-throw, ejection, timeout, and lifecycle controls through checked event transitions: linked captures are atomic, event ids project directly to shot markers, actor selection persists without entering fingerprints, and failures stay inline. BKE-2A adds tracked/opponent late participants, sequential regulation and dynamic overtime controls, local completion, and generalized Recent Events. BKE-2B adds unlocated direct shots/free throws, standalone related stats and turnovers, signed manual minutes, quick/official score adjustments, and optional atomic Steal + Turnover attribution. BKE-2C adds structured fouls and linked free-throw trips, official player/staff ejections, charged/neutral timeouts, projected disqualification/inventory, and dependency-aware correction/restore. BKE-2D completes tracker parity with projection-derived current-period foul/bonus presentation, consistent inactive-period court/grid/administrative guards, local Suspend/Abandon/reasoned-Reopen controls, and mixed-flow hydration/reprojection coverage. `courtCorrections.ts` groups same-command events for newest-first Undo/Restore, treats lifecycle rows as visible non-undoable boundaries, stores one validated fingerprint-inert reload-safe restore receipt, and performs dependency-aware shot/decrement corrections with exact relationship handling. BKE-2 is complete and BKE-3 owns editable Timeline/F13 work. Ordinary Basketball games retain the legacy reducer path; existing/team/cloud games cannot convert, corrupt marked games remain quarantined, and event cloud writes remain disabled. Migration 042 still rejects neutral cloud event rows until BKE-4A.
- **Basketball Timeline/F13 plan (BKE-3):** `docs/PLAN_BKE_3_EVENT_TIMELINE_AND_F13.md` is approved in four slices. BKE-3A adds Track/Timeline tabs, filtered capture-group review, shared read-only shot detail, marker selection, and legacy core marker detail. BKE-3B adds checked arbitrary remove/restore with conservative dependent restoration. BKE-3C delivers F13 shot, location, and assist/rebound/block editing. BKE-3D adds the remaining event-family editors, append-ordered recorded-later additions, and the exit audit. The current event engine retains revision metadata but not prior value snapshots; BKE-3 does not add a second audit store. Terminal games require reasoned Reopen before mutation, and lifecycle/identity events stay read-only. BKE-3 event behavior remains internal and local-only; BKE-4B begins cloud transport while event-game creation stays behind the internal gate through BKE-4E.
- **Soccer match workspace (SOC-2B/SOC-2C):** Active soccer games route `/setup`, `/players`, and `/game` to `SoccerGameSetup`, `SoccerPlayerSetup`, and `SoccerGameTracker`; legacy `/checkout` redirects into that flow, while `/summary` uses the SOC-6A soccer summary. Existing local/cloud Soccer routes remain reachable regardless of release stage or the device toggle. Setup snapshots per-match rules and either a local roster or read-only cloud source; kickoff atomically appends opening-lineup, period-start, and clock-start events. The live tracker renders the anchored clock without per-second reducer writes and delegates checked transitions to `src/lib/soccer/live.ts`. It supports period controls, substitutions, roles, direction/rules, late participants, revisioned correction history, diagnostics, and end/reopen.
- **Soccer attacking domain (SOC-3A):** `src/lib/soccer/` registers `soccer.shot`, `soccer.own_goal`, and `soccer.score_adjustment`. Score, side totals, attacking stats, and goalkeeper stats are event-derived. Actor `participantId` is the stable match identity; `playerId` may be resolved later. Explicit started-period/end-time projection plus on-field and role intervals validate historical attribution without advancing the live clock. The field capture, score controls, markers, and unified Timeline remain SOC-3B/SOC-3C; soccer remains local-only and development-only until later phases.
- **Soccer live field capture (SOC-3B):** The Soccer Game Tracker defaults to a full-pitch Field tab with explicit Tracked/Opponent capture side, persisted tracked-participant selection, a display-only 180-degree flip, and side-aware shot/own-goal attribution. Field taps and quick unknown-location Goal actions append checked soccer events through `src/lib/soccer/live.ts`; score remains projection-derived. Markers, unified Timeline filters, revisioned attacking-event editing, historical attacking adds, and score adjustments remain SOC-3C. Soccer remains local-only and development-only until later phases.
- **Soccer Timeline and field review (SOC-3C):** Located shots and own goals render as side-colored, outcome-shaped field markers with side plus current-period/full-match filters; selecting a marker opens the shared attacking editor. The Timeline replaces History with revisioned correction, bounded historical additions, remove/restore, and period-local `MM:SS`. Tapping either score opens scoring history and signed reason-required score adjustments. Invalid revisions remain visible through projection diagnostics; new historical appends must project completely.
- **Soccer core match events (SOC-4A/SOC-4B/SOC-4C):** `SoccerSportGameState` version 2 normalizes legacy availability flags into resolved tie rules and persists the Shot/Defense/Foul field capture preference. `src/lib/soccer/soc4.ts` owns defensive/foul/card/team-event projection, temporal discipline dependencies, restart-source validation, shootout eligibility, and structured results. Setup exposes editable IFAB/U.S. High School/Custom profiles. Normal play has three field modes, compact quick actions, all-family markers, focused event sheets, and expanded Timeline review. Tied winner-required matches enter the dedicated shootout setup/workspace through `src/lib/soccer/shootout.ts`; normal and shootout scores remain separate, kicks are revisioned, eligibility and goalkeeper changes are enforced, and completion/reopen are explicit. Cloud finalization remains SOC-5; soccer remains local-only and development-only.
- **Soccer cloud lifecycle (SOC-5A through SOC-6A):** Migrations `043_soccer_event_cloud_transport.sql` through `046_soccer_finalization_recovery.sql` add idempotent binding, immutable setup/participants, recorder checkpoints, same-recorder recovery/conflicts, independent team streams, provisional primary resolution, canonical publication, and audited reopen. `cloudSync.ts` pulls before upload and uses `bind_soccer_event_game_v4`; Cloud Games resumes matching local bindings before cloud access. `recorders.ts` keeps other streams isolated; `finalization.ts` reloads and projects only the cloud primary before the owner/admin transaction locks it. `game_event_canonical_publications` is append-only: reopen invalidates the active row and unlocks primary without deleting history. SOC-6A established one `/#/summary` authority path for local, effective-primary, and canonical-final review and initially shipped Overview; direct cloud review never hydrates `GameContext`, and legacy `/#/soccer/review` redirects with safe query context. Diagnostics retain last coherent context but suppress comparisons, leaders, and finalization. Final games reject normal capture, while pre-finalization non-primary queue entries may finish as audit-only rows without changing canonical output. Soccer remains development-only until SOC-6E.
- **Soccer summary Players (SOC-6B1):** `/#/summary?tab=players` derives every tracked participant from the selected summary source through `src/lib/soccer/summaryPlayers.ts`. It preserves match `participantId`, starter/substitute/DNP ordering, live second-precision minutes, role/on-field intervals, normal-match category totals, read-time rates, and fail-closed goalkeeper clean-sheet context. Opponent review stays team-only until complete opponent lineup/interval data exists. The optional Other recordings control loads one isolated read-only `cloud_recording`; streams never blend, Finalize is hidden until Primary is restored, and an owned cloud stream must open a local binding before editing.
- **Soccer summary Timeline (SOC-6B2):** `/#/summary?tab=timeline` derives an oldest-first, period-grouped normal-match review through `src/lib/soccer/summaryTimeline.ts`. Eight overlapping family filters classify every SOC-3/SOC-4 event; shootout kicks stay out while lifecycle context remains. Effective events show by default, removed events stay collapsed, and corrected rows expose only current revision metadata. `SoccerTimeline` shares located shot/incident correction dialogs with Field review: only an editable local source can add, revise, remove, or restore through checked helpers; cloud primary, canonical, and alternate recordings omit mutation controls.
- **Soccer summary Field (SOC-6B3):** `/#/summary?tab=field` derives normal-match attacking, defensive, restart, and discipline events through `src/lib/soccer/summaryField.ts`. It supports per-event normalized or original coordinates, side/multi-family/participant/period filters, deterministic overlap clusters, filter-aware unknown-location review, and event detail. Only an editable local source exposes the shared located-event editor; remote primary, canonical, and alternate recordings remain read-only. Unlocated events remain authoritative in Timeline/totals, and shootout activity stays out of Field.
- **Soccer summary Shootout (SOC-6B4):** `/#/summary?tab=shootout` appears only after a shootout starts and derives round-paired attempts through `src/lib/soccer/summaryShootout.ts`. It preserves non-advancing retakes, forfeits, early decisions, sudden death, stable anonymous slots, and game-scoped kicker/goalkeeper summaries without changing normal score, Players rates, or clean sheets. Attempt detail is read-only for every authority; correction remains in the owned local tracker. Unhealthy sources suppress all detailed tabs.
- **Soccer canonical aggregates (SOC-6C):** `aggregateStats.ts` and `aggregateProjection.ts` own the exact `soc_*` catalog and pure canonical cross-match projection. Migration `047_soccer_canonical_aggregate_sources.sql` exposes only RLS-scoped, keyset-paginated active completed publications, repairs only provable audited merge lineage, and makes future player merges remount `game_participants.source_player_id`. `aggregateTransport.ts` drains scope/player pages with validation, isolates malformed items as partial quality, separates per-consumer cancellation from shared in-flight requests, projects in cooperative batches, and reports progress, typed capability/access failures, and structured metrics; completed results are never cached. `useSoccerAggregateDestination.ts` and the soccer aggregate components route Leaderboard, Team Stats, Tournament Stats, Player Profile, and Career Stats through canonical scopes with best-effort roster rows, stable-player selection, category/rate presentation, canonical game/season history, manager-only diagnostics, and guarded manual/focus refresh. Participation always renders for player destinations; other all-zero categories stay hidden. Soccer route guards run before legacy aggregate RPCs, preserving non-soccer behavior.
- **Soccer settings (SOC-6D1 through SOC-6D4):** `src/lib/soccer/settings.ts` defines schema-version-1 personal/team/display settings, rejects persisted `extraTimeAvailable` / `shootoutAvailable` mirrors, and resolves built-in -> personal -> team -> match layers with source metadata and whole-layer diagnostics. Segment arrays are atomic fields. Migration `048_soccer_settings_foundation.sql` adds generic `user_sport_settings` / `team_sport_settings`, read-only RLS, strict soccer validation, compare-and-swap RPC writes, owner/admin team enforcement, and transactional `soccer_settings_changed` audit events. `useSoccerPersonalSettings` mounts cache-first personal settings in `SettingsContext`: anonymous and user-keyed scopes stay isolated, authenticated saves use revision CAS, offline failures remain pending, focus/online/Refresh reconcile, and conflicts require Use Cloud or Keep This Device. Team caches are account/team scoped; `useSoccerTeamSettings` keeps shared edits online-only. Team Manage lets owners/admins edit or copy sparse shared defaults and gives scorers/viewers read-only review. Soccer Match Setup resolves the full hierarchy with field sources, preserves explicit match overrides across team changes, retains old setup snapshots until deliberate edits, and writes a complete fixed `rulesSnapshot` on Continue. Corrupt/unsupported caches fail closed, browser storage failures retain session state with a visible warning, and the settings/setup controls include keyboard tab behavior, live status announcements, reset confirmation, and narrow-screen safeguards. See `docs/REGRESSION_SOC_6D_SETTINGS.md`.
- **Soccer release policy (SOC-6E1/SOC-6E3):** `src/lib/sportAvailability.ts` separates release stage, device discovery/new-game permission, and existing-record access. Soccer is released as a production opt-in but remains disabled in device settings by default; development preview follows the same stored toggle. Existing local/cloud setup, tracker, Summary, Game Info, and Cloud Games routes never use release state as a visibility gate. Migration `049_soccer_release_capabilities.sql` adds the authenticated read-only cloud contract handshake; `src/lib/soccer/releaseCapabilities.ts` strictly parses it and keeps an account-scoped in-memory success cache. Team Info, team setup deep links, and Soccer cloud-source Continue preflight capabilities before parking/replacing a game or committing cloud authority, with an explicit local-only fallback.
- **Soccer release hardening (SOC-6E2/SOC-6E3):** `docs/REGRESSION_SOC_6E_RELEASE.md` is the consolidated automated/manual release record. Legacy `statkeeper_settings` values are runtime-sanitized so malformed truthy Soccer values fail closed. Direct `import.meta.env.DEV` use is contract-tested and limited to centralized sport policy, the shot-chart preview, and aggregate diagnostics. The owner approved an owner-only, default-off production rollout with post-deployment validation; browser/PWA, role, cloud, multi-sport, and Basketball evidence remains required before access materially broadens.
- **Team Info hierarchy:** `/team?teamId=` is the canonical cloud team hub. `/teams` is list/create plus pending invites; `/team/manage?teamId=` hosts roster/member management and merge access. Team drill-downs are `/team/roster`, `/team/schedule`, `/team/season`, `/game-info`, and `/player-info`, all query-param based. Team Info Start Game links to `/setup?teamId=`; Leaderboard only backs to Team Info when `from=team` is present.
- **Team-level stats (basketball):** Optional `teamCategories` on `SportConfig`; local pseudo-player ids `__team_home__` / `__team_opp__` (`src/lib/teamPlayers.ts`). Season rules: `seasons.team_stats_config`, edited in **Settings → Data & Sync → Seasons** (`SeasonTeamStatsEditor`). Cloud: placeholder rows on `players`, `games.home_team_player_id` / `opp_team_player_id`, RPC `get_game_team_stats`. Game Summary tab **Team stats** when any team stat exists. Design: `docs/completed/DESIGN_TEAM_STATS_*.md`.
